# Arquitectura limpia para un backend moderno con Django REST Framework

> Guía base para construir un backend moderno, escalable, reutilizable y fácil de mantener usando **Django + Django REST Framework**.

---

## 1. Objetivo

La aplicación debe mantener una separación clara entre:

- Configuración del proyecto.
- Dominio.
- Casos de uso.
- Persistencia.
- API REST.
- Validaciones.
- Servicios externos.

Principios principales:

- Evitar lógica de negocio dentro de las views.
- Evitar lógica compleja dentro de serializers.
- Evitar acceso directo a modelos desde cualquier parte del proyecto.
- Separar responsabilidades.
- Reutilizar lógica.
- Mantener módulos independientes.
- Facilitar pruebas.
- Evitar duplicación.
- Mantener una estructura que pueda crecer sin volverse difícil de mantener.

```text
├── repositories.py
```

Ejemplo de entidad:


# 7. Repositorios como contrato

En el dominio se puede definir qué operaciones necesita la aplicación.

Ejemplo:

```python
from abc import ABC, abstractmethod

class UserRepository(ABC):

    @abstractmethod
    def get_by_id(self, user_id: int):
        pass

    @abstractmethod
    def create(self, data):
        pass

    @abstractmethod
    def update(self, user_id: int, data):
        pass

    @abstractmethod
    def delete(self, user_id: int):
        pass
```

La aplicación conoce el contrato.

La infraestructura implementa ese contrato.

# 9. Implementación del repositorio

```python
from apps.users.domain.repositories import UserRepository
from apps.users.infrastructure.models import User

class DjangoUserRepository(UserRepository):

    def get_by_id(self, user_id):
        return User.objects.filter(id=user_id).first()

    def create(self, data):
        return User.objects.create(**data)

    def update(self, user_id, data):
        user = User.objects.get(id=user_id)

        for field, value in data.items():
            setattr(user, field, value)

        user.save()

        return user

    def delete(self, user_id):
        return User.objects.filter(id=user_id).delete()
```

# 11. Caso de uso

Ejemplo:

```python
class CreateUserUseCase:

    def __init__(self, repository):
        self.repository = repository

    def execute(self, data):
        if not data.get("email"):
            raise ValueError("El correo es obligatorio.")

        return self.repository.create(data)
```

La lógica importante no debe estar en la view.

---

# 12. Views

Las views deben ser pequeñas.

Correcto:

```python
class UserCreateView(APIView):

    def post(self, request):
        serializer = UserCreateSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)

        repository = DjangoUserRepository()
        use_case = CreateUserUseCase(repository)

        user = use_case.execute(serializer.validated_data)

        return Response(
            UserSerializer(user).data,
            status=status.HTTP_201_CREATED,
        )
```

Evitar:

```python
class UserCreateView(APIView):

    def post(self, request):
        # validar 40 cosas
        # consultar 5 tablas
        # enviar email
        # crear usuario
        # registrar auditoría
        # aplicar reglas de negocio
        # devolver respuesta
```

La view no debe convertirse en el centro de toda la lógica.

---

# 13. Serializers

Los serializers deben encargarse principalmente de:

- Validar datos de entrada.
- Transformar datos.
- Serializar respuestas.

Ejemplo:

```python
from rest_framework import serializers

class UserCreateSerializer(serializers.Serializer):
    name = serializers.CharField(max_length=150)
    email = serializers.EmailField()
```

Evitar colocar lógica de negocio grande dentro del serializer.

---

# 14. Selectors

Los `selectors` se utilizan para consultas de lectura.

Ejemplo:

```python
from apps.users.infrastructure.models import User

def get_active_users():
    return User.objects.filter(is_active=True)
```

Esto evita repetir consultas complejas.

---

# 15. Services

Los services contienen lógica reutilizable que no necesariamente representa un solo caso de uso.

Ejemplo:

```python
class UserService:

    def normalize_email(self, email):
        return email.strip().lower()
```

# 24. Manejo global de errores

Crear un handler global.

Ejemplo:

```python
from rest_framework.views import exception_handler

def custom_exception_handler(exc, context):
    response = exception_handler(exc, context)

    if response is None:
        return response

    response.data = {
        "success": False,
        "message": "Ocurrió un error.",
        "errors": response.data,
    }

    return response
```

Configurar:

```python
REST_FRAMEWORK = {
    "EXCEPTION_HANDLER": "common.exceptions.custom_exception_handler",
}
```

# 43. Evitar lógica en models

Los modelos pueden contener lógica simple relacionada directamente con la entidad.

Pero evitar:

```python

        # crear pagos

        # registrar auditoría
```

# 44. Evitar señales para lógica crítica

No usar señales Django para procesos críticos difíciles de seguir.

Evitar:

```text

   ↓

   ↓
actualiza inventario
   ↓
manda email
```

si el flujo es fundamental para el negocio.

Preferir un caso de uso explícito:

```text

```

# 45. Evitar consultas N+1

Incorrecto:

```python

```

```python

    "customer"
)
```

Para relaciones múltiples:

```python
.prefetch_related(...)
```

# 54. Reglas estrictas para una IA o Codex

Cuando una IA trabaje sobre este backend debe respetar estas reglas.

## Arquitectura

1. No cambiar la estructura del proyecto sin una razón técnica clara.
2. Mantener cada dominio dentro de `apps/`.
3. No crear una app nueva si la funcionalidad pertenece claramente a una existente.
4. No crear una app por cada tabla.
5. Mantener separación entre `domain`, `application`, `infrastructure` y `api`.

## Views

6. Las views deben ser pequeñas.
7. No colocar lógica de negocio compleja en views.
8. No realizar procesos grandes directamente en endpoints.
9. Las views deben coordinar request, validación, use case y response.

## Serializers

10. Los serializers deben validar y transformar datos.
11. No colocar lógica compleja de negocio dentro de serializers.
12. Reutilizar serializers cuando corresponda.
13. Evitar serializers gigantes.

## Models

14. Los models representan persistencia.
15. No convertir modelos en servicios.
16. No colocar procesos completos dentro de models.
17. Mantener restricciones e índices correctamente definidos.

## Casos de uso

18. Toda lógica importante debe vivir en application/use_cases o services.
19. Los casos de uso deben tener una responsabilidad clara.
20. Evitar casos de uso gigantes.
21. Evitar duplicar reglas de negocio.

## Repositorios

22. El acceso complejo a datos debe estar encapsulado.
23. No repetir queries complejas en varias views.
24. Crear selectors o repositories reutilizables.
25. Evitar acceso desordenado al ORM.

## API

26. Mantener rutas consistentes.
27. Utilizar versionado `/api/v1/`.
28. Mantener respuestas consistentes.
29. Manejar errores de forma global.
30. Utilizar códigos HTTP correctos.

## Seguridad

31. Nunca exponer claves o secrets.
32. Nunca guardar passwords en texto plano.
33. Verificar permisos siempre en backend.
34. No confiar en validaciones del frontend.
35. Mantener CORS restringido.
36. No devolver stack traces al cliente en producción.

## Base de datos

37. Evitar N+1.
38. Usar `select_related` y `prefetch_related` cuando corresponda.
39. Utilizar transacciones cuando varias operaciones dependan entre sí.
40. Agregar índices cuando una consulta frecuente lo necesite.
41. Evitar consultas repetidas.

## Código

# 57. Regla práctica final

Para cualquier nueva funcionalidad, seguir este flujo:

```text
¿Es entrada/salida HTTP?
        ↓
      api/

¿Es lógica de negocio?
        ↓
 application/

¿Es una regla o contrato puro?
        ↓
     domain/

¿Usa Django ORM, archivos o servicios externos?
        ↓
 infrastructure/
```

Si una clase o función empieza a mezclar varias de esas responsabilidades, dividirla antes de seguir creciendo.
